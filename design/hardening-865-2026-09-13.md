# Hardening pass for argus#865 (13 Sep 2026)

Branch `fix/hardening-865`. Six defects found on production traces from Third Eye Trading, filed as argus#865, plus the learner failure in argus#583. Not deployed: pushing `main` is the deploy.

## 1. Market holidays

**What broke.** Mon 7 Sep 2026 was Labor Day. `is_trading_day` in `core/agent_config.py` checks the configured weekday and nothing else. Premarket `a356735b` and intraday `b32757c8` / `127234aa` all ran, and `b32757c8` placed WFC, JNJ, PRU and SNOW. Alpaca accepted them with no fill.

**Change.** New module `core/market_calendar.py` with `check_market_day(date) -> MarketDay(open, source, reason)`. It never raises. Resolution order:

1. Alpaca's calendar through the existing trading client (`core/alpaca.py::get_market_session_dates`, which calls `TradingClient.get_calendar`). A date is open when Alpaca lists a session for it. Successful answers are memoised per process; failures are not.
2. If that call fails, a static NYSE full-closure list for 2026 and 2027 (observed dates, so 3 Jul 2026 and 5 Jul 2027 are in it).
3. If the API fails and the date is outside the static list: **closed**.

**Fail closed, and why.** The two errors cost different things. A wrong "closed" skips one paper-trading day, with nothing bought and nothing at risk, and the skip is traced with source `unknown` and an alert. A wrong "open" sends orders into a closed market, which is the 7 Sep defect itself. Fail closed only fires when neither the API nor the list can answer. A transient Alpaca outage on a covered date still trades normally, because the list answers. A test (`TRIPWIRE_the_list_covers_the_current_year`) fails once the year runs past 2027, so the list gets extended before the fallback quietly stops covering anything.

**Callers.** Each checks the calendar right after the weekday check:

| Session | On a closed day |
|---|---|
| `sessions/premarket.py` | Traced. Opens one session, logs a `market_closed` skip for market, scanner, research, risk and orchestrator, a `market_closed` decision carrying date, source and reason, and closes with terminal_reason `market_closed`. Skip type is `design` for a holiday and `error` for a fail-closed day, which also sends an alert. The check sits after the dedup guard, and `market_closed` counts as a completed run, so a second cron fire writes nothing. |
| `sessions/intraday.py` | Log line and exit, placed above the `_premarket_main(bypass_checks=True)` fallback, which skips premarket's own checks. |
| `sessions/position_watchdog.py` | Log line and exit. The heartbeat still records, so standing down is not mistaken for a dead poller. |
| `sessions/eod.py` | Log line and exit, before it would reuse the premarket session id, overwrite `market_closed` with `eod_complete`, and queue market sells for the next open. |
| `sessions/watchdog.py` | Health checks return nothing on a closed day, so a holiday does not alarm "no EOD performance recorded". |

Only premarket writes a trace. The 15-minute polls already leave pass-through exits untraced ("only open a session when agents will actually run"), and 26 empty sessions per holiday would say nothing the first one does not. Premarket is the day's anchor session, so one `market_closed` record covers the day.

`premarket.py --bypass-checks` still skips the calendar along with its other guards. That flag is for manual end-to-end runs.

**Tests.** `tests/core/test_market_calendar.py`: Labor Day 2026 is closed, Tue 8 Sep 2026 is open, API first, API outranks the list, failure on a covered date uses the list, failure on an uncovered weekday fails closed, weekends, the list's shape, and the tripwire. `tests/conftest.py` now has an autouse fixture that gives session tests an open market, so their results do not depend on the day the suite runs. Calendar tests opt out with `@pytest.mark.real_calendar`.

## 2. Approved picks that vanish

**What broke.** In `_place_intraday_trades`, two gates skipped a risk-approved ticker with a `print()` and nothing else: "already entered today" and "already held at the broker". Production shows the pattern. In `b32757c8` risk approved six picks and five order traces exist. The later scan `127234aa` approved the same six and wrote one order trace: four were blocked by the same-day gate, and VLO was skipped again. PSX was approved and not submitted in scans on 8, 9, 10 and 11 Sep. Both are energy names entered on earlier days (VLO on 4 Sep), which fits the broker-held gate. That is an inference from session summaries and order-trace counts. I did not read `c_positions` to confirm it.

**Change.** Every approved ticker now ends in exactly one traced outcome:

- an order trace (`filled`, `accepted` or `rejected`), as before, or
- a skip trace: `log_skip("orchestrator", reason=<gate>, entity_id=<ticker>)`, with reasons `already_entered_today`, `already_held_at_broker` or `no_matching_proposal`. The last covers an approved verdict whose ticker has no proposal, which also dropped silently.

`TraceLogger.log_skip` gained optional `entity_id` and `detail`, so the skip settles at the ticker grain like the order does. A failing skip trace is caught and never stops the scan. A duplicate proposal for a ticker already handled in the same batch is ignored without overwriting the first outcome.

## 3. Session metadata

**What broke.** `_close_intraday` never passed `trades_approved` to `close_session`, so it defaulted to 0. The result summary put the entered count in front of the approved list: "4 trade(s): VLO, WFC, MU, JNJ, PRU, SNOW".

**Change.** `close_session` now gets `trades_approved` and `risk_rejections` from the verdicts. The summary comes from `_entry_summary` and names entered tickers only, then gives the counts, then the approved picks that were not entered and why:

`4 entered: WFC, JNJ, PRU, SNOW. Risk approved 6, rejected 1. Approved but not entered: VLO (already_held_at_broker), MU (rejected).`

## 4. The claim

**What broke.** Each intraday entry claimed `realized_pnl = (target - entry) * shares`, the profit if the target is hit, with HIGH mapped to confidence 0.9. A claim that assumes the win can never forecast a loss.

**Choice.** The value is now an expected value over the bracket's two exits, using the agent's own stated confidence as the probability:

`EV = p * (target - entry) * shares - (1 - p) * (entry - stop) * shares`, with p from HIGH 0.9 / MEDIUM 0.6 / LOW 0.3.

The claim's `confidence` is the probability of the claimed sign: p when EV is zero or above, 1 - p when it is negative. Value and confidence now come from the same number and cannot contradict each other. A LOW pick at 1.5 to 1 claims a negative value, which is what "30% sure" implies.

**This probability is not calibrated, and the note says so plainly.** `confidence_backtest.py` found HIGH names hitting direction 27% of the time against 56% for LOW. I considered claiming only the sign, since the mapping is not a real probability. I chose EV for three reasons. It is the agent's stated belief, which is exactly what a claim should record. It can predict a loss. And because the claim is honest about what the agent believed, Provy's overclaim rate on HIGH picks will measure the miscalibration instead of hiding it. Recalibrating the mapping is a strategy change and was left alone.

Bracket exits only: a trailing stop or the EOD force-close can settle between stop and target. When there is no stated confidence, no claim is sent. A value of 0 would claim break-even, which nobody said.

**Schema.** Provy reads `signal`, `value`, `confidence` and `entity_id`. On the claim path it parses `value` as any scalar and grades it against the contract's condition (`realized_pnl gt 0`). It does not compare dollar amounts, and it does not read the sign on its own. Confidence is clamped to [0, 1]. The four keys and their types are unchanged. The payload still carries `estimated_profit` (at target) and `max_loss`, and adds `expected_value`.

## 5. Learner

**What broke.** Turn 1 is the learner's reads. In turn 2 it issues its `write_learning` calls, and 2048 output tokens could not hold them, so the loop stopped on `max_tokens`. The writes were the part that got cut off, so nothing reached `c_learnings`.

**Change.**
- `run_tool_loop` takes `max_tokens` (default 2048, unchanged for other agents) and `max_tokens_ceiling` (default 16000). A `max_tokens` stop below the ceiling is retried with double the budget. The truncated response is not appended and its tool calls are not run, because the last one may carry partial input and half a `write_learning` or `adjust_param` is worse than none. Each retry spends a turn and logs a `max_tokens_retry` decision, so the 20-turn limit still bounds the loop. Truncation at the ceiling still fails fast with a message that names the ceiling.
- The learner starts at 8192 with a 16000 ceiling. Its prompt now caps output at 5 learnings, each finding under 300 characters, no narration, and the summary as bare JSON.
- The learner's result now includes `learnings_confirmed`, the number of `write_learning` calls the database accepted. EOD logs it next to the model's own `learnings_written`, which the model reports about itself. On #583 nothing compared the two, so a month with no rows went unnoticed.

Whether learnings actually land will only show on the first EOD after deploy. Tests prove the loop now survives a truncated write turn and runs the complete call. They cannot prove Haiku fits its output into 8192 tokens on a real day.

## 6. Units

`_entry_rationale` said "size 3000.0" for a dollar amount. It now says "$3,000 position".

## Not done

- **Positions carried past EOD.** `sessions/eod.py::get_open_positions` filters `open_date == today`, so a position opened on an earlier day and still open is never force-closed, and `close_all_strategy_positions` is skipped whenever today has no open rows. This is the likely reason VLO and PSX stayed held and kept hitting the broker gate. Fixing it changes when positions exit, which is outside this pass.
- **Early closes.** 13:00 ET sessions (day after Thanksgiving, Christmas Eve) count as open days. EOD at 15:55 runs after the close on those days. The Alpaca calendar returns the close time, so this could be added.
- **`max_new` in intraday** is computed and never enforced. Not part of #865.
- **Premarket and opening orders** make no per-ticker claim, now or before.
